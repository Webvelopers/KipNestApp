# KipNest encryption

KipNest encrypts file content and file details (name, type, size, creation date) in three independent layers, on top of TLS. Each layer has its own keys and its own algorithm. Implementations: [src/server/crypto.js](../src/server/crypto.js) (server, `node:crypto`) and `src/client/crypto.js` (browser, Web Crypto; in a release it is bundled into `dist/client/assets/app.js`). They must stay byte-for-byte compatible; the integration tests run the browser module against the real server.

## Threat model

**Assets:** stored file content, and file details (name, type, size, date).

**Protected against:**

- A network observer or a TLS-terminating proxy, passive or active: the token is never sent (the browser proves it knows a key derived from it), every request is signed with a session key, and content, details, file lists, and storage stats travel encrypted under ephemeral session keys. A proxy that does not know the token can neither open a session nor impersonate the server (both sides prove knowledge of the token key).
- Traffic analysis of sizes: upload and download bodies, the encrypted upload header, and sealed replies are padded, so traffic reveals a 64 KiB size bucket (1 KiB for headers and replies), not exact sizes or name lengths.
- Someone who reads the upload folder (`storage/uploads/` or `UPLOAD_DIR`) or its backups without `.env`: content and details are encrypted with keys derived from `STORAGE_KEY`; stored sizes only reveal a 64 KiB bucket, and file timestamps are all set to 2000-01-01.
- Tampering anywhere (in transit or on disk): every chunk is authenticated, and chunk order, truncation, extra data, and swapping files between ids are detected.
- A passive observer who later learns the token: sessions use ephemeral ECDH keys, so recorded sessions cannot be decrypted with the token alone (forward secrecy).

**Not protected against:**

- A compromised server process: it decrypts uploads in memory to validate them (required by the "never trust the client" rule) and re-encrypts downloads.
- Offline guessing of a **weak** token by someone who records a handshake: the client proof is an HMAC under the PBKDF2-derived token key, so a short or human-chosen token could be brute-forced offline (600 000 PBKDF2 rounds per guess). The generated 256-bit tokens from `npm run setup` make this infeasible; keep using them.
- The number of files, the size bucket, and the moment of a request are visible to the server and to anyone watching traffic volume.
- Malicious code running inside the page (XSS), or a compromised browser.
- Someone who has both the upload folder and `STORAGE_KEY`.

## Keys

| Key | Derivation | Lives in |
| --- | --- | --- |
| Token key | PBKDF2-SHA-256(`UPLOAD_TOKEN`, `KDF_SALT`, 600 000 iterations) → 32 bytes | Server memory; browser memory as a non-extractable HMAC-SHA-256 key |
| Session key | HKDF-SHA-256(ikm = ECDH P-256 shared secret, salt = HMAC-SHA-256(token key, sessionSalt), info = `kipnest/v1/session`) → 32 bytes | Server memory (sessions map); browser memory as a non-extractable HKDF key |
| Request key | HKDF-SHA-256(session key, empty salt, `kipnest/v1/request-auth`) → 32 bytes, used as an HMAC-SHA-256 key | Server memory; browser memory as a non-extractable HMAC key |
| Upload key | HKDF-SHA-256(session key, salt = fileNonce, `kipnest/v1/upload`) → 32 bytes | Per upload |
| Sealed JSON key | HKDF-SHA-256(session key, salt = nonce, `kipnest/v1/<label>`), label `list`, `stats`, or `receipt` → 32 bytes | Per reply |
| Download keys | HKDF-SHA-384(session key, salt = downloadNonce, `kipnest/v1/download/<purpose>/<id>`) → 76 bytes = encKey(32) ‖ macKey(32) ‖ ivBase(12) | Per download or preview |
| Wrap key | HKDF-SHA-512(`STORAGE_KEY`, empty salt, `kipnest/v1/kek-wrap`) → 32 bytes | Server memory |
| Metadata root key | HKDF-SHA-512(`STORAGE_KEY`, empty salt, `kipnest/v1/kek-meta`) → 32 bytes | Server memory |
| `kekId` | HKDF-SHA-512(`STORAGE_KEY`, empty salt, `kipnest/v1/kek-id`) → 8 bytes; public, tells which key wrote a file | Every `.bin` and `.meta` header |
| DEK | 32 random bytes per stored file, wrapped with the wrap key | Inside each `.bin` header |
| Metadata key | HKDF-SHA-512(metadata root key, salt = file id, `kipnest/v1/meta`) → 32 bytes | Derived on use |

`STORAGE_KEY` (32 bytes) and `KDF_SALT` (16 bytes) are base64url values in `.env`, generated by `npm run setup`. `STORAGE_KEY_PREVIOUS` holds older keys during a rotation; they can decrypt but never encrypt.

## Handshake: `POST /api/session`

The token itself never leaves the browser.

1. The browser creates an ephemeral P-256 key pair and sends `{ "publicKey": base64url(65-byte uncompressed point), "timestamp": ms, "proof": base64url(HMAC-SHA-256(token key, "kipnest/v1/client-proof" ‖ clientPublic ‖ u64 BE timestamp)) }`, with no `Authorization` header. The timestamp uses the server clock: `/api/config` returns `serverTime`, and the browser keeps the offset.
2. The server checks the proof in constant time and that the timestamp is within 5 minutes; a failure is `401` and counts toward the brute-force block. Each proof is accepted only once (a replayed handshake gets `400`). Handshakes are limited per address (30 per minute by default, `429` beyond).
3. The server creates its own ephemeral pair, a random 32-byte `sessionSalt`, and a random 16-byte `sessionId`, and replies `{ sessionId, publicKey, salt, proof, expiresIn }`, where `proof = HMAC-SHA-256(token key, "kipnest/v1/server-proof" ‖ clientPublic ‖ serverPublic ‖ sessionSalt)`.
4. The browser checks the server proof (constant time) before deriving anything. A substituted server key fails here.
5. Both sides derive the session key and the request key (table above).

## Request authentication

Every API request except `GET /api/config` and the handshake carries:

- `X-Session-Id`: the session id.
- `X-Request-Time`: milliseconds, server clock (within 5 minutes).
- `X-Request-Nonce`: 16 random bytes (base64url), accepted only once per session.
- `X-Request-Mac`: base64url(HMAC-SHA-256(request key, these lines joined with LF: `kipnest/v1/request`, method, path with query, time, request nonce, `X-Download-Nonce` value, `Range` value)); absent headers count as empty lines.

A signed request can therefore not be replayed, moved to another path or query, or have its download nonce or range changed.

A missing or unknown session returns `401` with `"code": "session"` (the browser opens a new session and retries once; not counted as a failed login). A known session with a bad or stale signature returns `401` and counts toward the brute-force block; a reused request nonce returns `401` ("already used"). An upload body (`KNU1`) must be encrypted for the same session that signed the request.

Sessions live in server memory for `max(15 min, upload timeout + 60 s)` after their last use, and never longer than 12 hours in total. Signing out (`DELETE /api/session`, a signed request) removes the session at once. At most 1000 sessions are kept (the least recently used is evicted first), and each accepts at most 10 000 uploads before the browser must open a new one.

## Brute-force protection

10 failed proofs (handshake or request) from one address within a minute block it with `429` and `Retry-After`. The block applies only where proofs are checked: new handshakes and invalid request signatures. Correctly signed requests from an open session and `GET /api/config` are never blocked, so an attacker who shares the owner's address (NAT, proxy, same /64) can delay new sign-ins but cannot cut off an open session. Each new block doubles (1 min, 2 min, 4 min, … up to 1 hour) until the address stays clean for 24 hours; a successful handshake resets it. Addresses are normalized first: IPv4-mapped IPv6 (`::ffff:a.b.c.d`) counts as IPv4, and IPv6 addresses are grouped by /64.

## Transit layer: uploads (`KNU1`)

Sent as the content of the multipart field `archivo` (filename `upload.knu`).

```text
"KNU1" (4) | sessionId (16) | fileNonce (16) | headerLength u32 BE | header ciphertext
then records: flag (1) | length u32 BE | ciphertext + GCM tag (16)
```

- Cipher: AES-256-GCM with the upload key. IV = 4 zero bytes ‖ u64 BE index; index 0 is the header, records use 1..n. Each upload key is unique (fresh `fileNonce`), so counters never repeat under one key.
- Header plaintext: JSON `{ name, size, chunkSize: 1048576 }`, space-padded to a multiple of 1024 bytes (so the name length does not show), AAD = prefix (36 bytes) ‖ `"header"`. The server ignores any client MIME type.
- Records: 1 MiB of plaintext each. The last record carries the rest of the file zero-padded to a multiple of 64 KiB; the server keeps only `size` bytes. `flag` is 1 exactly on the record where the rest fits, and every record's length must match. AAD = prefix ‖ u64 BE index ‖ flag.
- The server rejects a bad tag, a wrong flag or length, a missing final record, data after it, a size different from the header, an unknown session, or a `fileNonce` already seen in this session (replay). A nonce is burned even when the upload fails, so the browser re-encrypts on every retry.
- The encrypted receipt is a sealed JSON reply (`receipt`).

## Validation without plaintext on disk

`busboy → transit decryptor → validator → rest encryptor → <id>.part → rename <id>.bin`. The validator sniffs the first 4100 bytes with `file-type` (PNG, JPEG, PDF) or checks strict UTF-8 and control characters chunk by chunk (TXT). Plaintext only exists in memory, one chunk at a time. Size limits apply to plaintext; the quota is checked against the final encrypted size before anything is stored.

## Rest layer: stored content (`KNR1`, `<id>.bin`)

```text
"KNR1" (4) | kekId (8) | wrapIv (12) | AES-256-GCM(wrap key, DEK) + tag (48) | noncePrefix (4)      = 76 bytes
then fixed-size records: flag (1) | ChaCha20-Poly1305 ciphertext (65 536) | tag (16)
```

- DEK wrapping AAD: `"KNR1"` ‖ file id ‖ kekId ‖ noncePrefix, so a `.bin` cannot be moved to another id and its header fields cannot be altered.
- Records: ChaCha20-Poly1305 with the DEK, nonce = noncePrefix ‖ u64 BE index, AAD = `"KNR1"` ‖ id ‖ u64 BE index ‖ flag. The last record has flag 1.
- Padding: the last chunk is zero-padded to 64 KiB. File size on disk = `76 + ceil(size / 65536) × 65553`. The real size lives in the encrypted details.
- Fixed-size records give random access, which the download layer uses to serve ranges.
- `.bin` and `.meta` modification and access times are set to 2000-01-01 after every write, so the file system does not reveal upload dates.

## Encrypted details (`KNM1`, `<id>.meta`)

```text
"KNM1" (4) | kekId (8) | iv (12) | ChaCha20-Poly1305 ciphertext | tag (16)
```

Plaintext: JSON `{ id, name, size, type, createdAt }`, space-padded to a multiple of 256 bytes. Key: the metadata key; AAD = `"KNM1"` ‖ id ‖ kekId. The decrypted `id` must match the file name, so details cannot be swapped between files.

## Sealed JSON replies (`KNL1`)

`{ nonce, data }`, both base64url. `data` = AES-256-GCM(sealed JSON key, IV = 12 zero bytes, AAD = `"KNL1"` ‖ label) of the JSON value, space-padded to a multiple of 1024 bytes, plus tag. The key is unique per random 16-byte nonce, and the label in the AAD keeps one kind of reply from being passed off as another. Used for the file list (`list`), storage stats (`stats`), and the upload receipt (`receipt`).

## Download layer: downloads and previews (`KND1`)

Requested with a signed request (see Request authentication) and a fresh random 16-byte `X-Download-Nonce`.

```text
"KND1" (4) | header ciphertext (1024) | HMAC (64)
then records j = 1..n: ciphertext (1 MiB; the last one zero-padded to a 64 KiB multiple) | HMAC (64)
```

The header holds the real size; the browser drops the padding after verifying the last record.

- Cipher: AES-256-CTR with encKey. Counter block for record j (header j = 0) = ivBase ‖ u32 BE (j × 65 536); each record uses at most 65 536 blocks, so keystreams never overlap. The 32-bit counter caps files at 65 535 MiB.
- MAC: HMAC-SHA-512(macKey, `"KND1"` ‖ id ‖ purpose byte (`d` download, `p` preview) ‖ nonce ‖ u32 BE j ‖ flag ‖ ciphertext), flag = 2 for the header, 1 for the last record, 0 otherwise. The browser verifies each MAC before decrypting (encrypt-then-MAC).
- Header plaintext: JSON `{ name, type, size, chunkSize: 1048576 }`, space-padded to 1024 bytes.
- The layout is deterministic for a given nonce, so `Range` requests over the encrypted body work. The browser resumes from the last verified record with `Range: bytes=<offset>-`, reusing the same nonce (same keystream, same plaintext, so nothing new is revealed).
- Responses are `application/octet-stream`, `attachment; filename="<id>.knd"`, `no-store`, `same-origin`. Only the page can turn them back into the original file.

## Maintenance

- `npm run encrypt:migrate [-- --dry-run]` (`scripts/encrypt-storage.js`): encrypts plaintext pairs (`<id>.<ext>` + `<id>.json`) from older versions, verifies the encrypted copy by decrypting and hashing it, then deletes the plaintext. Idempotent; failures leave originals untouched. The server refuses to start while plaintext files remain.
- `npm run encrypt:rotate`: re-wraps each DEK and re-encrypts each `.meta` with the current `STORAGE_KEY`, using `STORAGE_KEY_PREVIOUS` to read. Content records are copied unchanged.

## Limits and invariants

- No plaintext content or details are ever written to disk or sent outside these layers.
- All tag and MAC checks fail closed with generic errors (`400 The upload could not be verified.`, or a closed connection mid-download); nothing reveals which check failed.
- Nonce uniqueness: upload, sealed-JSON, and download keys are derived per random nonce; rest nonces are per-file DEKs with counters; metadata uses a random 96-bit IV under a per-file key.
- Maximum file size: 65 535 MiB (download counter); the configured `MAX_FILE_MB` is far below it.
- The browser bounds the PBKDF2 cost it accepts from `/api/config` (1000 to 10 000 000) and only accepts 1 MiB download records.
- Browser memory: uploads are built record by record into a `Blob` (the browser may keep it outside the JavaScript heap); true request streaming is not possible because browsers only stream request bodies over HTTP/2. Downloads of 50 MB or more are written straight to disk with the File System Access API where available (Chromium); otherwise the decrypted file is held as a `Blob`. The server side is fully streamed.
- Migration deletes plaintext with a normal file deletion. Earlier copies may survive in free disk blocks, snapshots, or backups; wipe or rotate those separately if that matters.
